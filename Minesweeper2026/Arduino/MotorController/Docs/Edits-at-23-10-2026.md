## Executive Summary

On October 23, 2026, a comprehensive technical code review and hardening pass was conducted across the `MotorController` firmware. The review targeted real-time responsiveness, safety interlocks, floating-point precision on 8-bit AVR architecture, serial communications integrity, and peripheral GPIO alignment with the as-built robot wiring (Safi configuration).

A total of **12 core firmware files** were modified to address critical bugs, eliminate CPU blocking bottlenecks, and ensure 100% interoperability with both the ROS2 `ros2_control` hardware interface and the ESP8266 WiFi Web Controller.

## Detailed Technical Analysis & Implementation

### 1. Gripper Velocity Default Hijacking & Lift Auto-Aborting (E1)

#### Root Cause
In `SystemManager::update()`, local variables `r_vel`, `l_vel`, `g_vel`, `s_angle` are declared each cycle:
```cpp
float r_vel = 0.0f, l_vel = 0.0f, g_vel = 0.0f, s_angle = -1.0f;
if (serial_.processInput(r_vel, l_vel, g_vel, s_angle)) {
    motion_.setRightTarget(r_vel);
    motion_.setLeftTarget(l_vel);
#if ENABLE_LIFT
    lift_.handleVelocityCommand(g_vel); // BUG: g_vel is 0.0f if packet had no 'g' token!
#endif
```
When driving the robot via the WiFi web interface or ROS teleop, drive packets are sent at high frequency (`rp05.00,lp05.00,`). Because these packets contain no `g` token, `g_vel` remained `0.0f`. Inside `LiftController::handleVelocityCommand(float g_vel)`:
```cpp
if (g_vel > 0.1f) { raise(); }
else if (g_vel < -0.1f) { lower(); }
else {
    if (manual_active_) { stop(); } // <-- Instantly cancelled ongoing lift operations!
}
```
Consequently, whenever an operator commanded `LIFT:UP` or pressed the lift button while simultaneously steering the robot, the very next drive packet (within 20–70 ms) aborted the lift movement.

#### Implementation Details
1. **Added `has_gripper_cmd` Parameter:**
   `SerialProtocol::processInput()` now accepts `bool& has_gripper_cmd`:
   ```cpp
   bool processInput(float& right_vel, float& left_vel, float& gripper_vel, bool& has_gripper_cmd, float& servo_angle);
   ```
   `has_gripper_cmd` is set to `true` **only** if a valid `gp` or `gn` token was parsed in the inbound packet.
2. **Gated Gripper Execution in `SystemManager`:**
   ```cpp
   #if ENABLE_LIFT
   if (has_g_cmd) {
       lift_.handleVelocityCommand(g_vel);
   }
   #endif
   ```
3. **Continuous Joystick State Isolation in `LiftController`:**
   Added `bool manual_joystick_active_` to `LiftController`:
   * Discrete commands (`raise()`, `lower()`, `CLIFT:UP`, `CLIFT:DN`) set `manual_active_ = true` and `manual_joystick_active_ = false`.
   * Continuous joystick commands set both `manual_active_ = true` and `manual_joystick_active_ = true`.
   * When joystick velocity returns to zero (`|g_vel| <= 0.1f`), the controller stops the motor **only if `manual_joystick_active_` was true**, ensuring ROS teleop release stops the motor without cancelling discrete full-travel commands.

### 2. Floating-Point Truncation with Integer `abs()` on AVR (E2)

#### Root Cause
Under the AVR-GCC toolchain, `abs()` is defined in `<stdlib.h>` for integers (`int abs(int)`). Unless `<math.h>` is explicitly included and `fabsf()` is used, passing a floating-point argument implicitly truncates the float to `int`.

* **Impact on Odometry (`Odometry.cpp`):**
  ```cpp
  if (abs(omega_robot) < 1e-6) // Evaluates abs(int(omega_robot))
  ```
  Any angular velocity where $|\omega_{\text{robot}}| < 1.0\text{ rad/s}$ (approx. $57.3^\circ/\text{s}$) truncated to `0`. As a result, the condition `0 < 1e-6` evaluated to `true`, and the robot integrated almost **all normal steering maneuvers as straight-line motion**, completely corrupting dead-reckoning odometry.
* **Impact on Safety Monitor (`Safety.cpp`):**
  ```cpp
  if (abs(right_pwm) > STALL_PWM_THRESHOLD && abs(right_vel) < STALL_VEL_THRESHOLD)
  ```
  When the robot was moving under load at $0.8\text{ rad/s}$, `abs(right_vel)` truncated to `0`. Because $0 < 0.05$, the firmware falsely flagged a motor stall.

#### Implementation Details
* Added `#include <math.h>` and replaced all instances with `fabsf()` in:
  * `MotionController.cpp`: velocity clamping, deadband checking, and `isStopped()`.
  * `Safety.cpp`: right/left motor stall detection.
  * `Odometry.cpp`: linear and angular kinematics integration.
  * `MotorDriver.h` & `MotorDriver.cpp`: output deadband checking and PWM magnitude calculation.

### 3. Latching Emergency Stop (E-Stop) Security (E3)

#### Root Cause
In `SystemManager::update()`:
```cpp
if (safety_.getState() == SystemState::ESTOP) {
    safety_.clearEStop(); // BUG: Drive packet auto-cleared E-Stop!
}
safety_.forceState(SystemState::RUNNING);
```
If an operator clicked E-Stop or the safety monitor tripped, incoming drive packets published at 50 Hz by ROS2 (`rover_interface`) automatically cleared the E-Stop within 20 ms.

#### Implementation Details
* Removed automatic E-Stop clearing in `SystemManager::update()`.
* When the system is in `SystemState::ESTOP` or `SystemState::SHUTDOWN`, drive commands are ignored.
* E-Stop can now **only be cleared** by sending an explicit extended serial command:
  * `CCLEAR` $\rightarrow$ clears E-Stop and resets fault flags.
  * `CRESET` $\rightarrow$ clears E-Stop, resets faults, resets odometry, and zeroes IMU yaw.

### 4. Isolated Stream Parsers for `Serial` and `Serial2` (E4)

#### Root Cause
In `SerialProtocol.h`, `token_buffer_` (64 bytes) and `token_index_` were single shared member variables. When `processInput()` sequentially polled `Serial` (USB) and `Serial2` (ESP8266), a partial packet on one port (e.g. `rp1.`) would have bytes from the second port appended to it, corrupting command tokens.

#### Implementation Details
Encapsulated an isolated stream parser state:
```cpp
struct StreamParserState {
    char token_buffer[64];
    uint8_t token_index;
};
StreamParserState parser_serial_;
#if ENABLE_SERIAL2
StreamParserState parser_serial2_;
#endif
```
`readStream(Stream& port, StreamParserState& parser)` processes each UART port into its own dedicated buffer, preventing buffer collisions.

### 5. Pin 27 Metal Detector Conflict & Siren Pin 47 Mirror Removal (E5)

#### Root Cause
* In `Config.h`:
  ```cpp
  constexpr uint8_t PROXIMITY_PINS[] = {23, 25, 27, 29, 31}; // Pin 27 is Prox 3
  constexpr uint8_t METAL_DETECTOR = 33;
  ```
* In `Sensors.cpp`:
  ```cpp
  bool current_reading = (digitalRead(Pins::METAL_DETECTOR) == SensorConfig::METAL_ACTIVE_STATE) ||
                         (digitalRead(27) == SensorConfig::METAL_ACTIVE_STATE);
  ```
  Whenever an obstacle triggered Proximity Sensor 3 (D27), the code also evaluated `metal_detected_ = true`, activating the 12V alert siren and triggering unwanted mine retrieval cycles.
* Legacy test code in `Sensors.cpp` also drove Pin 47 alongside Pin 37 (`Pins::BUZZER`).

#### Implementation Details
* Removed `pinMode(27, INPUT)` and `digitalRead(27)` from `Sensors.cpp`. Metal detection is now strictly tied to `Pins::METAL_DETECTOR` (Pin 33).
* Removed all references and `digitalWrite` calls to Pin 47.

### 6. Non-Blocking Ultrasonic Timeout Bounding (E6)

#### Root Cause
In `Sensors::measureUltrasonicCm()`:
```cpp
unsigned long duration = pulseIn(Pins::US_ECHO, HIGH, 25000UL); // 25 ms timeout
```
`pulseIn()` is a blocking busy-wait function. If the HC-SR04 ultrasonic echo pulse was lost (e.g. grass/sand absorption or sensor unplugged), the CPU froze for 25 milliseconds. Because tasks in `SystemManager` run cooperatively on a single thread, this 25 ms stall delayed the 20 ms PID velocity control loop.

#### Implementation Details
* Bounded the timeout to `SensorConfig::US_MAX_ECHO_US` (6,000 $\mu$s $\approx$ 100 cm range).
* Because the gripper ultrasonic sensor is positioned to detect mines inside the scoop at $\le 15\text{ cm}$ (echo return $\approx 870\ \mu\text{s}$), a 6,000 $\mu$s timeout preserves detection while capping maximum worst-case loop blocking to 6 ms.

### 7. Serial TX Buffer Overflow Protection & Telemetry Rate Harmonization (E7)

#### Root Cause
At 115,200 baud, transmitting ~55 bytes takes $\approx 4.77\text{ ms}$. Broadcasting this packet at 100 Hz (`TELEMETRY_INTERVAL_MS = 10`) across two ports (`Serial` and `Serial2`) filled Arduino's 64-byte hardware TX buffer, causing `println()` to enter blocking wait loops and consuming over 75% of CPU cycles.

#### Implementation Details
1. **TX Buffer Availability Check:**
   Updated `sendStringToPort()` to verify buffer capacity before writing:
   ```cpp
   static void sendStringToPort(HardwareSerial& port, const char* str) {
       size_t len = strlen(str) + 2; // includes \r\n
       if (port.availableForWrite() >= len) {
           port.println(str);
       }
   }
   ```
2. **Telemetry Rate Harmonization:**
   Updated `Timing::TELEMETRY_INTERVAL_MS = 20` (50 Hz) in `Config.h`. This aligns telemetry with the 50 Hz PID loop and matches the default `ros2_control` update frequency without saturating the serial bus.

### 8. Dynamic Delta-Time ($\Delta t$) in Velocity Calculation (E8)

#### Root Cause
`SystemManager::taskControlLoop()` previously computed velocity using a fixed constant:
```cpp
float dt = Timing::CONTROL_INTERVAL_MS / 1000.0f; // Always 0.020s
```
Under cooperative task execution, minor scheduler jitter (e.g. 2–4 ms variation from I2C reads or sensor filtering) meant the accumulated encoder pulse count represented a 22–24 ms window, introducing up to 20% error in calculated wheel velocity.

#### Implementation Details
Implemented dynamic cycle timing using `micros()`:
```cpp
static uint32_t last_control_us = 0;
uint32_t now_us = micros();
float dt = (last_control_us > 0) ? (now_us - last_control_us) * 1e-6f : (Timing::CONTROL_INTERVAL_MS / 1000.0f);
last_control_us = now_us;

// Sane bounding guard
if (dt < 0.005f) dt = 0.005f;
if (dt > 0.100f) dt = 0.100f;
```

### 9. Hardware Limit Switch Pin Harmonization & Struct Packing (E9)

#### Root Cause
* In `Config.h`, the file docstring on line 181 stated `Limit Switches: Top 53, Bottom 51`, while lines 211–212 defined `LIMIT_SW_TOP = 51` and `LIMIT_SW_BOTTOM = 53`.
* In `Docs/Pinout.md`, Top is defined as D51 and Bottom as D53.
* `struct RobotParameters` lacked explicit memory packing, creating potential struct alignment issues across different compiler versions.

#### Implementation Details
* Corrected docstrings and inline comments in `Config.h` to consistently specify **Top = 51** and **Bottom = 53**.
* Added `__attribute__((packed))` to `struct RobotParameters` in `Config.h`.

---

### 10. Lift State Machine Fault Latching (E10)

#### Root Cause
In `LiftController.cpp`:
```cpp
case LiftState::FAULT:
    stopMotor();
    state_ = LiftState::IDLE; // BUG: Immediately reset to IDLE in 10 ms!
    break;
```
When a motor stall timeout occurred, the controller transitioned to `FAULT`, but on the very next 10 ms cycle, `state_` was overwritten back to `IDLE`, masking faults from telemetry and diagnostics.

#### Implementation Details
Removed the automatic transition to `IDLE`. The controller now remains in `LiftState::FAULT` with the motor halted until the operator sends a `CCLEAR` command or initiates a manual recovery motion.

## Bench Testing & Commissioning Checklist

Before deploying the rover to the test field, perform the following verification steps:

- [ ] **Dual-Port Serial Verification:** Connect USB Serial to PC (115,200 baud) and connect to the ESP8266 WiFi Access Point. Verify commands sent via Web Controller do not disrupt or drop packets on USB Serial.
- [ ] **Simultaneous Drive & Lift Test:** Command forward drive (`rp03.00,lp03.00,`). While wheels are spinning, issue `CLIFT:UP`. Verify the lift actuator moves upward continuously without stalling or stopping early.
- [ ] **Latching E-Stop Verification:** While driving, issue `CESTOP`. Verify motors immediately halt and telemetry reports `ESTOP`. Continue sending drive commands; verify motors remain stopped. Send `CCLEAR` and verify normal drive resumes.
- [ ] **Ultrasonic Disconnection Test:** Unplug HC-SR04 Echo jumper wire (Pin 45) while driving. Verify drive motors maintain smooth 50 Hz PWM without stuttering or timing dropouts.
- [ ] **Proximity Sensor 3 Isolation Test:** Trigger Proximity Sensor 3 (D27) with an obstacle. Verify `p1` telemetry is reported, but metal detection telemetry (`m0`) and the 12V siren remain inactive.
- [ ] **Metal Detector Test:** Bring a metal target near the search coil (Pin 33). Verify `m1` is reported, the 12V siren sounds for 1.5 seconds, and the magnet relay energizes.
